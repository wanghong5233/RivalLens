# LLM 调用参数成熟化(方法论修正版)

## 方法论(本 plan 的根基,已与用户确认)

旧 plan 用全历史 p99 反推配置 = 错(系统未成熟、历史数据混入重构前噪声,不可信)。修正为:

1. **主依据 = 业界任务分档锚点**,不依赖本仓数据。
2. **最新真实数据 = 下限地板**(配置必须 ≥ 实测成功延迟,否则误杀),且只取今天的数据。
3. 锚点天然高于地板就用锚点;地板顶破锚点才抬高。

数据角色降级为"参考 + 兜底",不作推导公式。

### 业界锚点(来源)

- connect 超时 = 5s:httpx 官方 + livekit/anthropic [#5529](https://github.com/livekit/agents/pull/5529) + langchain/openai [#36949](https://github.com/langchain-ai/langchain/pull/36949) 一致——单值 timeout 把 per-chunk read 也设死会误杀 thinking/prefill,须 connect 紧、read 宽。
- read 超时分档:短决策 60s / 中结构化 90-120s / 长生成 180s(OpenAI/Anthropic SDK 默认 600s 偏松,生产 agent 普遍按任务收紧)。
- max_tokens = 取 `≥ 2× 实测输出` 并向上取 2 的幂(防截断 + 留余量惯例)。

### 最新地板(仅今天成功调用,作校验非推导)

| slot | 今天 max 延迟 | 今天 max 输出 tok |
|---|---|---|
| summarization | 94.6s | 2064 |
| writer | 56.5s | 3676 |
| qa | 25.9s | 1618 |
| research | 18.0s | 1027 |
| compression | 14.8s | 821 |

(历史 research max=80s 是旧数据噪声,今天仅 18s,印证只信最新。)

## 定档表(锚点为主 + 地板校验)

| slot | 任务类 | read 超时 | 地板校验 | max_tokens | 依据 |
|---|---|---|---|---|---|
| summarization | 大结构化输出 | 180s | 94.6s ✓ 2x 余量 | 4096 | 锚点;地板顶到中档上沿→按长档 |
| writer | 长报告 | 180s(保持) | 56.5s ✓ | 8192 | 锚点主导,deep 报告输出大 |
| compression | 中结构化 | 120s | 14.8s ✓ | 2048 | 锚点主导 |
| qa | 中结构化 | 90s | 25.9s ✓ | 2048 | 锚点主导 |
| research | 短决策(最频繁) | 90s | 18s ✓ | 2048 | 60s 锚点 + ReAct 尾部余量 |
| connect(全局) | — | 5s | — | — | 业界范式 |

确认 30s 偏小这一结论与数据噪声无关:summarization 地板就 94.6s,30s 必然误杀。

## 现状代码锚点

- 超时仅 writer 特判,其余共用 30s:

```49:52:backend/app/service/llm/client.py
def _resolve_timeout_seconds(model_slot: str) -> int:
    if model_slot == "writer":
        return settings.LLM_TIMEOUT_WRITER
    return settings.LLM_TIMEOUT_SECONDS
```

- provider 传单值 timeout(SDK 展开成 connect=read=write 全相等):

```267:274:backend/app/service/llm/providers.py
    kwargs: dict[str, Any] = {
        "model": model,
        "messages": [...],
        "timeout": timeout_seconds,
    }
```

- `max_tokens` 全仓 grep 无任何设置点(输出无上限,是延迟偏高根因之一)。
- token 估算 `chars/3 + 1024` 在 [rate_limiter.py](backend/app/service/llm/rate_limiter.py) `estimate_tokens`,因无 max_tokens 实际输出常超估算,但仅影响 TPM(默认关),本轮不动。

## Stage 1 — 按 slot 分层超时

- [config.py](backend/app/core/config.py)(现状 L51-57 扁平风格):新增 `LLM_TIMEOUT_SUMMARIZATION=180` / `LLM_TIMEOUT_COMPRESSION=120` / `LLM_TIMEOUT_RESEARCH=90` / `LLM_TIMEOUT_QA=90`,`LLM_TIMEOUT_WRITER` 保持 180,`LLM_TIMEOUT_SECONDS` 保留为兜底默认;新增 `LLM_CONNECT_TIMEOUT_SECONDS=5`;在 `validate_llm_provider_credentials` 加正数校验(对齐现有 timeout 校验块)。
- [client.py](backend/app/service/llm/client.py) `_resolve_timeout_seconds`:从"仅 writer 特判"改为按 slot 查表,未命中回落 `LLM_TIMEOUT_SECONDS`。

## Stage 2 — provider connect/read 拆分

- [providers.py](backend/app/service/llm/providers.py) `_create_completion`:`"timeout": timeout_seconds` → `httpx.Timeout(connect=settings.LLM_CONNECT_TIMEOUT_SECONDS, read=float(timeout_seconds), write=10.0, pool=5.0)`。read 宽(承接 slot 档位)、connect 紧。

## Stage 3 — max_tokens 兜底

- [config.py](backend/app/core/config.py):新增 per-slot `LLM_MAX_TOKENS_SUMMARIZATION=4096` / `WRITER=8192` / `COMPRESSION=2048` / `QA=2048` / `RESEARCH=2048`;`0` 表示不限。
- [client.py](backend/app/service/llm/client.py):`complete_json` 解析 slot 对应 max_tokens,透传至 provider。
- [providers.py](backend/app/service/llm/providers.py) `_create_completion`:`max_tokens > 0` 时注入 kwargs;JSON-mode 失败回退路径(同函数内第二次 `_create_completion`)同步带 max_tokens。
- 防截断:所有 max_tokens 已 ≥ 2× 今天实测 max 输出,不会切断 JSON。

## Stage 4 — 同步 + 验证

- [.env.example](.env.example):补全新增 env 占位,注释标注"业界锚点 + 最新地板"依据。`.env.dev` 用户自管,不改。
- 单测 [test_llm_client.py](backend/app/tests/test_llm_client.py) / [test_llm_providers.py](backend/app/tests/test_llm_providers.py):per-slot 超时查表(命中 + 回落)、`httpx.Timeout` connect/read 分项断言、max_tokens 注入 + JSON-mode 回退仍带 max_tokens。
- docker 定向 pytest + 一次性探针实测 summarization/research,确认不再贴 30s 线、输出有上限、comparisons 正常。

## 明确不做(成熟判断,非遗漏)

- 展示/日志截断(preview 180/220/300、error trim 500/2000):不影响正确性。
- 业务循环上限(`MAX_REACT_TURNS=6`、`MAX_QA_REJECTIONS=3`、`MAX_SUPERVISOR_ITERATIONS=10`、fan-out cap 8):经设计且集中在 [defaults.py](backend/app/core/defaults.py)。
- curator 阈值、metrics 比率:S6 刚定。
- harness `max_repair_attempts=1`、TPM budget=0、压缩预算双处定义:各有归属,不在本轮。
- 不用历史数据反推任何值(方法论红线)。
