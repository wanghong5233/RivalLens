# 群答疑与出题人信号

> 本文记录飞书群、导师答疑、出题人解释中出现的补充信息。原始问答与“信号提炼”分开写，避免把主观判断混进赛题事实源。

## 2026-05-20：竞品分析面向用户与范围控制

### 原始上下文

有同学围绕“竞品分析面向的用户群体和分析的竞品类型是否有偏好、后续报告关注侧重点和需要配备的数据源”进行提问。

### 问题背景摘要

竞品分析一般不是某一个岗位专属，而是围绕产品决策、市场决策、销售决策、投资决策服务。常见用户包括：

- 产品经理 / 产品负责人
- 创业者 / CEO / 项目负责人
- 市场 / 增长 / 商业化团队
- 销售 / 售前 / 客户成功团队
- 投资人 / 战略分析师 / 行业研究员
- 设计师 / 用户体验团队

不同用户关注点不同：

- 产品经理关注功能、交互、定价、用户反馈和差异化。
- 创业者关注市场机会、进入时机、竞争格局、细分用户和商业模式。
- 市场 / 增长团队关注定价、卖点、营销切口、官网对比页和投放文案。
- 销售 / 售前团队关注竞品报价、弱点、销售话术中的差异回答。
- 投资人 / 战略分析师关注市场规模、壁垒、增长速度、竞争格局和潜在赢家。
- 设计 / 用户体验团队关注信息架构、交互路径、页面布局、视觉风格和转化链路。

### 出题人 / 研发答复原文

> 上交竞品雷达，比如：上图中六个类别选两类，来控制解题范围。实际很多场景是在产品经理和创业者、项目负责人方面。

### 可作为决策依据的信号

1. 题目不要求覆盖所有竞品分析用户类型，允许从典型用户类别中选取少数几类控制范围。
2. 出题人明确提到“六个类别选两类”，说明范围控制是被接受的，不应做泛泛全角色系统。
3. 出题人明确指出实际很多场景集中在“产品经理”和“创业者 / 项目负责人”方面，这两个用户类型应成为 RivalLens 的优先目标用户。
4. 系统报告侧重点应服务产品决策和创业/项目决策，而不是优先服务销售、投资、设计等所有场景。
5. 竞品类型可以保持通用，但“用户角色与报告目标”需要收敛，否则 Schema、数据源、报告结构都会发散。

### 对 RivalLens 的影响

RivalLens 的第一版应优先服务两类用户：

1. **产品经理 / 产品负责人**
   - 判断竞品功能能力、功能差异、用户反馈、定价策略和可借鉴点。
   - 报告需要突出 feature tree、pricing model、user feedback、differentiation。

2. **创业者 / CEO / 项目负责人**
   - 判断市场机会、切入细分用户、商业模式、竞争格局和产品定位。
   - 报告需要突出 market opportunity、positioning、business model、risk、SWOT。

暂不优先覆盖：

- 销售 / 售前话术型竞品分析。
- 投资 / 行业研究型深度报告。
- 设计 / UX 层面的竞品/标杆分析。
- 增长 / 投放素材型竞品分析。

这些可以作为扩展场景，不进入第一版核心闭环。

## 2026-05-20：垂类分析与通用能力边界

### 原始上下文

有同学问到是否可以做垂类竞品分析。

### 答疑补充

导师答疑表示可以做垂类，但倾向于系统具备通用性。不能只能完成一种竞品分析，而无法迁移到另一种竞品分析场景。Agent 系统本身希望具备泛用能力。

### 可作为决策依据的信号

1. 项目不能做成“只服务某一个垂直行业”的硬编码系统。
2. 可以选择具体垂类作为演示样例，但系统框架、Agent 协议、Schema 基座、报告流程需要具备可迁移性。
3. 需要区分“演示数据集/行业包”和“核心能力”。演示可以垂直，核心必须通用。
4. 第一版不应追求覆盖所有行业，但必须证明换行业、换竞品对象时不需要重写 Agent 主流程。

### 对 RivalLens 的影响

RivalLens 应采用“通用核心 + 场景配置”的方式：

- 通用核心：Agent DAG、结构化消息、证据模型、质检反馈闭环、Trace、报告生成流程。
- 可配置部分：竞品类型、行业字段、数据源模板、报告关注重点、质检规则。

第一版可以用一个主要行业做高质量演示，但必须在架构和文档中说明如何迁移到其他行业。

## 2026-05-20：开源项目与许可证限制

### 原始上下文

群内答疑提到可以使用开源项目或源码，但需要关注开源许可证。

### 答疑补充

可以使用 MIT、Apache-2.0、BSD 协议的开源项目或源码。

### 可作为决策依据的信号

1. 可以合理复用开源代码或项目，但必须保留许可证声明。
2. 不应引入 GPL / AGPL 等可能产生传染性或分发约束的源码。
3. 所有第三方依赖需要记录许可证，避免提交材料时出现合规风险。

### 对 RivalLens 的影响

后续技术选型必须保留依赖许可证清单。能用依赖包解决的问题不要复制源码；如确需复制样例代码，必须确认许可证为 MIT / Apache-2.0 / BSD，并在文档中记录来源。

## 2026-05-20：采集 Agent 是否包含问卷与访谈

### 原始问答

同学提问：

> 核心功能中提到采集 Agent 包含“问卷调研、用户访谈”，这部分是指 Agent 完全自动化地去寻找真实用户发问卷 / 做对话访谈，还是指 Agent 仅负责生成问卷标题目，或仅负责处理已有的真实访谈录音文本？

答复：

> 都行，你能做到完全自动找用户问卷回收更好。

### 可作为决策依据的信号

1. 采集 Agent 的“问卷/访谈”范围是开放的，可以是生成问卷、处理已有访谈文本，也可以是更完整的自动化问卷回收。
2. 出题人认为更完整的自动化问卷回收更优，但不是硬性要求。
3. 第一版可以用“已有公开评论/模拟访谈/问卷样本处理”保证可控性，同时保留扩展到真实问卷回收的接口。

### 对 RivalLens 的影响

RivalLens 第一版不应把真实用户招募和问卷回收作为核心依赖，否则三周内风险过高。更稳的设计是：

- 采集 Agent 支持三类输入：公开网页、用户评价/评论、问卷或访谈文本。
- 演示时可使用公开评论或预置访谈文本作为“用户声音”数据源。
- 文档中说明未来可接入问卷系统，实现自动问卷生成、投放、回收和分析。

## 2026-05-20：LangGraph / CrewAI 是否强制

### 原始问答

同学提问：

> 在这个项目中，是不是一定要使用那两个框架（LangGraph / CrewAI），还是说可以使用自己手搓的？谢谢您！

答复：

> 可以手搓，不限制。

### 可作为决策依据的信号

1. LangGraph / CrewAI 不是强制要求，可以自研编排。
2. 但题目材料和考察要点多次提到 LangGraph / CrewAI，说明评委会期待看到清晰的 DAG、Agent 状态流转和结构化消息，而不是随意拼 Prompt。
3. 手搓可以，但必须在可视化、可追溯、状态管理、反馈闭环上达到框架级清晰度，否则不如直接使用 LangGraph。

### 对 RivalLens 的影响

RivalLens 可以选择 LangGraph 或自研轻量 DAG。决策不应基于“炫技”，而应基于三周内的稳定交付：

- 如果使用 LangGraph：加分点是与考察要点对齐，DAG 语义清晰，评委理解成本低。
- 如果自研：必须额外写清 Agent 状态机、节点协议、边条件、重试和打回机制，且前端要能展示 DAG Trace。

初步倾向：除非团队对 LangGraph 集成出现明显阻塞，否则优先使用 LangGraph，避免在编排框架上消耗解释成本。

## 2026-05-20：是否需要支持并发

### 原始上下文

有同学询问项目是否需要支持并发。

### 答疑补充

导师回答：不强求，但是支持并发更好。

### 可作为决策依据的信号

1. 并发能力不是硬性验收要求，不应为了并发牺牲核心闭环稳定性。
2. 支持并发会被视为工程完整度和系统扩展性的加分项。
3. 并发不一定指高并发压测，也可以是任务级并发：多个竞品采集并行、多个数据源采集并行、多个 Agent 节点在可并行阶段并行执行。

### 对 RivalLens 的影响

RivalLens 第一版应优先保证单任务端到端闭环稳定，同时在架构上保留任务级并发：

- 采集阶段可并发抓取多个竞品 / 多个数据源。
- 分析阶段可按竞品或证据片段并行结构化。
- 报告撰写与质检保持串行或受控重试，避免状态混乱。
- 后端接口设计上保留 job/task/run_id，便于后续支持多个分析任务同时运行。

## 2026-05-20：导师举例的竞品分析场景

### 原始上下文

导师在讲解课题时，对"竞品分析"举的示例场景。

### 答疑补充

导师举的例子是："通用类型的 Agent 有哪些产品？"——即将"通用 AI Agent 产品赛道"作为典型的竞品分析对象。

### 可作为决策依据的信号

1. 导师脑中默认的 demo 心理模板就是"分析通用 Agent 产品"，评委评审时大概率会用同一心理模型对照演示。
2. AI Agent 产品赛道（含通用 Agent、编程 Agent、企业 Agent 平台、终端 Agent）成为天然贴合心理模板的演示行业。
3. 选择 AI Agent / AI Coding 工具作为主演示，能最大化与评委心理模型的对齐，降低评委的理解成本。

### 对 RivalLens 的影响

主演示行业锁定 **AI Agent 产品赛道**，主演示子集采用 **AI Coding 工具**（Cursor / Windsurf / TRAE / Claude Code），原因：

- 资料公开度最高，竞品官网 / 定价页 / 用户评论密集，Collector 与 Extractor 容易出活。
- 评委（字节工程团队）对赛道熟悉度极高，演示结论可被即时验证。
- 与赛题要求使用的 TRAE 工具形成叙事自洽：不是被迫用 TRAE，而是在用自己的系统分析包括 TRAE 在内的整个 AI Coding 赛道。
- 文档中需说明 Schema 字段、Collector 模板、报告章节如何平移到通用 Agent / 终端 Agent / 企业 Agent 平台，证明"通用核心 + 场景配置"。

## 2026-05-20：作品提交形式与界面要求

### 原始上下文

群内对作品最终提交形式与界面是否必要进行确认。

### 答疑补充

作品提交可以是录屏 demo 形式，同时必须具备用户友好的界面功能。

### 可作为决策依据的信号

1. 不要求公网部署 / 域名 / HTTPS / 云资源，可以仅在本地完成演示并通过录屏提交。
2. 界面不可缺，纯 CLI 或纯接口演示不符合要求。
3. UI 是评分 20% "业务价值与产品体验"里的硬性项，必须可演示、可交互、易理解。
4. 录屏可控性允许提前设计确定性的演示数据集与镜头剧本，但同样意味着评委对录屏中的卡顿、报错、不流畅容忍度更低。

### 对 RivalLens 的影响

- 可砍掉：公网部署、域名注册、HTTPS、K8s、复杂 CI/CD，全部不做。
- 不可砍：DAG 可视化、Trace 时间线、证据卡片、引用跳转、加载态、错误态。
- 时间分配：把原本"答辩准备 0.5 周"中的录屏粗剪提前到第 2.5 周开始，让录屏暴露的 UI 问题反向驱动前端打磨。
- 演示数据集与开发并行整理，不能等开发完最后凑。

## 2026-05-20：部署形态

### 原始上下文

群内对部署形态与是否需要云资源进行确认。

### 答疑补充

导师答复：本地 localhost 部署即可，无需公网与云资源。

### 可作为决策依据的信号

1. 部署成本（购买云、配域名、HTTPS）全部省略。
2. 后端可使用 SQLite + 本地文件 artifact 目录，不需要外置数据库 / 对象存储。
3. 前端可走 Vite dev server 或本地静态构建，不需要 CDN / Nginx 反代。
4. 录屏环境可以彻底受控，避免网络抖动 / 第三方依赖宕机造成的演示风险。

### 对 RivalLens 的影响

- 部署形态固化为：`docker compose up` 一键起后端 + 前端 + SQLite，本地端口跑通即可录屏。
- 不引入 Redis / PostgreSQL / Milvus / S3 / OSS / Kafka 等需要额外部署的中间件，除非核心闭环必须。
- 演示时通过本地静态资源 + 预置数据集模拟"真实采集"，避免现场依赖外网。
- 节省下来的部署时间预算全部转移到 UI 打磨与演示数据集打磨。

## 2026-05-20：数据脱敏要求

### 原始上下文

导师在讲解竞品分析时提到数据可能需要脱敏处理。

### 答疑补充

竞品分析涉及的数据（如用户评价、访谈内容、问卷数据等）可能需要进行脱敏处理。

### 可作为决策依据的信号

1. 评分 10% "合规、材料与答辩"里明确要求"用户访谈、问卷数据脱敏处理，无敏感信息泄露"，本条与评分项直接对齐。
2. 脱敏范围至少覆盖：用户名 / 头像 / 邮箱 / 手机号 / 真实姓名 / 公司内部信息。
3. 公开评论 / 公开网页内容本身合规，但仍需要避免将可识别个人信息直接写进报告或 Demo 数据集。

### 对 RivalLens 的影响

- 演示数据集来源以公开页面、公开评论、官方文档为主，避免使用任何来自私域 / 内部群 / 个人访谈的真实数据。
- 即使来源是公开评论，在 Extractor / Writer 阶段也要去除 / 替换原始用户 ID、用户名、头像 URL。
- 后端实现一个轻量的 `desensitize.py` 工具函数（手机号 / 邮箱 / 用户名正则替换 + 占位符），所有写入 evidence 表的文本字段统一过该函数。
- README + 合规声明中明确数据来源与脱敏策略，作为答辩材料的一部分。
