# 竞品分析根因修复（基于 run_8496e71e2869 审计）

## 背景与判定
真实复跑 `run_8496e71e2869`（同输入：`AI 硬件的主流产品以及发展趋势。` + `self_product=AI眼镜`）已验证 P0 状态机大成功：端到端 23.8min→7.8min、Supervisor 13→5、Analyze 8→1。剩余问题按根因分四项根治 + 一项止血。

用户已确认：宽口径 landscape 保留全部玩家、按角色分层（不丢弃）；source 可在风险可控下增搜索；竞品知识全 0 单列 plan。

## 两层架构定位（统一全局视角）
本轮修复落在第一层；竞品知识系统性根治是第二层，二者由 intake 入口衔接：
- **第一层 宽口径 / landscape**：用户要"看懂整个 AI 硬件全景"——趋势 + 按角色/品类分层（芯片/眼镜/汽车/机器人各自成段）。本轮 P1 做分层、P5 做诚实止血。
- **第二层 聚焦 / 具体产品**：从第一层分层结果下钻到具体产品，产出完整功能树/定价/画像/反馈知识 schema，并接入竞品追踪。属后续单列 plan。
- **intake 入口（根因起点）**：当前 intake Agent 只给"具体下游品类"选项，强迫用户收窄，缺"宽口径全景"这条路。修复方向是让用户选"宽口径全景"或"聚焦具体竞品/品类"，宽口径产出全景+分层后，用户再勾选感兴趣的具体产品进入第二层。intake 改造与第二层强耦合，归入后续单列 plan。

## P1：Discovery 角色纠偏（用于诚实标注与分层，宽口径不丢弃）
根因有两层，均已确认：
- `_discovery_search_queries`（[backend/app/agents/nodes/supervisor.py](backend/app/agents/nodes/supervisor.py)）只用 domain_context/user_query，宽口径下结果偏产业链——这是宽口径预期，保留。
- `_normalize_candidate_role`（[backend/app/agents/nodes/discovery.py](backend/app/agents/nodes/discovery.py)）拿到 LLM 合法值就采用，`_infer_candidate_role` 只在缺失时兜底，**不覆盖 LLM 误判**；prompt 已写"芯片标 upstream"但 LLM 无视，证明纯 prompt 无效。

改法：
- 新增 `_reconcile_candidate_role`：当名称/relevance_reason 命中强信号（`_DISCOVERY_UPSTREAM_HINTS` 芯片/GPU/算力、`_DISCOVERY_TREND_HINTS` 报告/媒体）时，**覆盖** LLM 的 `direct_competitor` 为 `upstream_supplier`/`trend_reference`；在 `_filter_discovery_candidates` 内对每个候选先纠偏再分类。
- `_filter_discovery_candidates` 增加 `analysis_archetype` 参数：comparison 模式维持现状（非 core 角色 `filtered_out`）；**landscape 模式保留非 core 角色**，仍按 `_DISCOVERY_ROLE_PRIORITY` 排序使 direct/adjacent 在前、upstream/trend 在后。
- `reconcile_plan_tree_after_discovery`（[backend/app/agents/nodes/planner.py](backend/app/agents/nodes/planner.py)）对 landscape 的非 core 候选设软上限（如 core 全保留 + 非 core 最多补到 `max_competitors`），避免产业链玩家挤占。
- 验收：同类 run 的 `competitor_sources` 角色不再全是 direct_competitor（芯片→upstream，网球机→substitute/trend）；宽口径仍覆盖芯片内容；research 队列 direct/adjacent 在前。

## P2：Golden 断言校准（修自相矛盾的回归门）
[backend/app/tests/golden/cases/16_ai_hardware_glasses_trajectory.yaml](backend/app/tests/golden/cases/16_ai_hardware_glasses_trajectory.yaml) 现含 `knowledge_feature_count_gte: 1` 与 `knowledge_schema_coverage_rate_gte: 0.2`，但真实 landscape run 实测 feature=0、coverage≈0，**断言对其来源 run 必然失败**。
- 移除这两条（landscape 知识三件套低产是预期，归入后续知识 plan 的回归门）。
- 保留并作为主回归门：`supervisor_iterations_lt: 8`、`analyze_count_lte: 2`、`report_section_count_gte: 4`、`source_authority_distribution_includes`。
- 可补 `analysis_archetype`/角色相关断言留待 P1 落地后。

## P3：QA 告警负样本（证明告警链路端到端可见）
当前 run QA 干净通过，`qa_warnings` 为空，**无法证明告警 UI 真会渲染**。`_qa_warning_items`+`content_json.qa_warnings` 写入逻辑已确认正确（仅非空写入）。
- 新增 golden case（参考已有 locale 用例 [backend/app/tests/golden/cases/14_locale_zh_domestic.yaml](backend/app/tests/golden/cases/14_locale_zh_domestic.yaml)），构造会触发 `rule_locale_mismatch` 的输入（强中国 market_scope + 易得国外源），断言 `qa_warnings_count_gte: 1` 且 `warning_rule_ids_includes: [rule_locale_mismatch]`、`final_qa_outcome: approved`。
- 这样 P2 的 QA 告警产品化获得真实回归门。

## P4：来源权威有限根治（拉起 official 占比）
根因：`resolve_official_sources`（[backend/app/service/collector/source_resolver.py](backend/app/service/collector/source_resolver.py)）的 `candidate_urls` 来自 `discovered_competitor_sources[x].official_url`，而 discovery 极少填到真官网（多为 null 或 sohu/eet-china 聚合页），导致 `source_authority` 全 third_party。
- 在 researcher（[backend/app/agents/nodes/researcher.py](backend/app/agents/nodes/researcher.py)）的 `_candidate_source_urls_for_competitor` 之外，新增一次定向"官网解析"搜索（如 `{competitor} 官网` / `{competitor} official site`），把命中的高分官方 URL 并入 `candidate_urls` 再交给 `resolve_official_sources` 验证。
- 复用现有 search channel，不引入重型采集；加 per-competitor 单次预算上限控制成本/时延。
- 验收：同类 run `source_authority_distribution` 不再 100% third_party，可识别到部分 official/authoritative_report；报告"数据缺口披露"随之收敛。

## P5：宽口径竞品知识止血（诚实 + 用户友好，非系统性根治）
landscape 趋势证据难抽每竞品三件套（已确认 `schema_extraction_mode=llm_structured` 正常返回但 0 条），当前仅 pricing 标 not_applicable，feature/persona/feedback 仍 insufficient_data，KnowledgePanel 一片"证据不足"像坏掉。
- [backend/app/service/knowledge/extractor.py](backend/app/service/knowledge/extractor.py)：landscape 模式下，当某竞品 feature/persona/feedback 均 0 grounded 时，标 `not_applicable_for_archetype`（与 pricing 一致），并写对应 missing_reason；metrics 覆盖率口径已排除该状态（[backend/app/service/metrics/engine.py](backend/app/service/metrics/engine.py:361) 已就绪）。
- [frontend/src/components/knowledge/KnowledgePanel.tsx](frontend/src/components/knowledge/KnowledgePanel.tsx)：landscape 时顶部加场景说明横幅（"本次为趋势/全景分析，竞品知识三件套为辅助视图，具体产品的功能/定价/画像需进入聚焦分析"），各空态文案区分"本场景不适用"与"证据不足"。
- 明确边界：这是止血，让 Demo 不像坏字段；真正"宽口径枚举具体产品 + 定向调研填充 schema + 接入竞品追踪"单列后续 plan。

## 后续单列 plan（竞品知识系统性根治 = 第二层 + intake 入口，本轮不做）
统一两层架构的完整链路：
- **intake 入口**：识别宽口径模糊输入，提供"宽口径全景 / 聚焦具体竞品或品类"路径，不再强迫收窄到单一下游品类。
- **第一层 → 第二层下钻**：趋势/全景分析同时枚举赛道代表性具体产品；用户从分层结果勾选关注对象，进入第二层。
- **第二层 定向调研填充 schema**：对具体产品做面向 feature/定价/画像/反馈的下钻调研（区别于第一层趋势新闻证据），填充知识三件套。
- **接入竞品追踪**：勾选发现的竞品加入 watchlist，形成"发现 → 知识 → 追踪"闭环。

横跨 intake/discovery/planner/researcher/knowledge/tracking，新增下钻链路与 intake 路径选择，体量与原六项打磨相当，复杂度高、回归风险中高，故单列。
